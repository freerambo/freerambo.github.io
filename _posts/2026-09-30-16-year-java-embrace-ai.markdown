> 以前我担心：AI 会不会替代程序员？
> 现在我更担心：不会用 AI 的程序员，会不会先被替代？

最近公司在推全栈，新增了全栈岗位。

消息一出，团队里聊得最多的不是技术，是焦虑：

- 前端是不是没了？
- 后端会不会也轮到？
- 所谓「AI 全栈工程师」，是不是就是一个人干三个人的活？
- AI 写出来的代码，质量谁来兜底？

我做 Java 第 16 年了。从Java Servlet、JSP、SSH 时代一路走到云原生，经历的"技术寒冬"没有十次也有八次。说完全不焦虑，是假的。

但把这件事认真想透之后，我得到了一个有点反直觉的结论：

**AI 没有替代我。相反，我已经越来越离不开它。**

---

## 01｜16 年里，我被时代"重新定义"过很多次

2010 年入行，写的是 SSH：Struts2 + Spring + Hibernate。一个页面一个 Action，一张表一套映射，XML 写到怀疑人生。那时候不是没有"全栈"这个词，而是人少活多，默认你什么都得会一点。

后来前后端分离来了，前端有了自己的工程体系，后端终于不用在 JSP 里拼 HTML。

再后来是 Spring Boot，是微服务：Dubbo、Spring Cloud、注册中心、配置中心、网关、熔断、限流、链路追踪……

2018 年之后是云原生：K8s、Service Mesh、DevOps、混沌工程。最近几年，又轮到中台、DDD、稳定性工程。

那十几年里，很多 Java 工程师都有过类似的夜晚：

> 白天写业务，晚上研究 Tomcat 到底是怎么加载如何启动的、Dubbo 为什么注册不上，顺手再翻一遍 Spring Cloud 的版本兼容表。一抬头，凌晨三点。

每一轮技术切换，都有人说：这波要淘汰一批人了。

后来呢？

**愿意学的人继续往前走，不愿意变的人被留在了原地。**

今天的 AI，本质上是又一次范式切换。只是这一次，动静比之前任何一次都大。

---

## 02｜AI 打破的不是岗位，是岗位边界

更准确的说法是：**AI 正在打破原本清晰的岗位边界。**

以前一个需求的链路，长这样：

```
产品提需求 → 前端做页面 → 后端写接口 → 测试验收 → 上线
```

每个环节都有明确的交接点，也都有明确的等待时间。

现在呢？一个懂业务、懂系统的工程师，可以借助 AI 把前半程压缩成一条线：

```
需求拆解 → 快速产出页面原型 → 定义接口与数据结构 → 生成前后端骨架代码 → 验证核心流程
```

这不代表某个角色不重要了。它代表的是：**过去需要多人、多轮协作才能跑通的第一版验证，现在一个人几天就能给出来。**

岗位结构的变化背后，真正在变的不是"前端没价值了"，而是企业开始更看重三件事：

- 谁能更快把需求落地
- 谁能跨越多个技术边界
- 谁能对最终结果负责

16 年的经验还让我看到一个规律：

**每一次工具革命，削掉的都是"工具人"环节，放大的是"判断人"环节。**

IDE 削掉了手写部署脚本，CI/CD 削掉了手工发版，云削掉了一部分运维——但每一次，"懂系统的人"都变得更贵了。

因为工具越强，判断越稀缺。

---

## 03｜现在做技术方案，我会先和 AI "吵一架"

以前写技术方案，我的固定动作是：拆业务流程、画模块边界、翻历史代码、找旧方案、想异常分支、列潜在风险。

现在这些我还是会做。只是我多了一个随时在线、不会嫌我问题多的"技术搭子"。

一个新需求进来，我会先让 AI 做第一轮推演：

- 这个需求可以怎么拆？
- 核心链路和异常链路分别是什么？
- 单体扩展、异步化、缓存、消息队列，各自适合什么场景？
- 表结构和接口应该怎么设计？
- 现有系统可能会踩到哪些坑？

它给的答案，往往不能直接用。有时候看起来很完整，实际上完全不适配我们的存量架构。

但它有一个极大的价值：

**它能在十分钟内，把我脑子里模糊的想法，变成一份可以被质疑、被讨论、被推翻的方案。**

以前这个过程要半天，现在只要半天的一半。

而 16 年经验的作用，在这里体现得最明显：**我知道 AI 会在哪里胡说八道。**

- 它谈分布式事务，常常一句"最终一致性"就带过，不会告诉你补偿逻辑谁写、幂等怎么做、消息丢了怎么办。
- 它做容量规划，喜欢拍一个很漂亮的 QPS，但不会问你峰值在什么时候、数据量一年涨几倍、缓存穿透了怎么兜。
- 它设计接口，倾向于把字段给全，但不会提醒你有些字段在合规上根本不能落库。

**AI 能生成一份看起来 85 分的方案。但一个系统从 85 分走到 99 分的那 14 分，才是真正的工程。**

所以我的用法很固定：**AI 出初稿，我来挑刺。它负责把可能性铺开，我负责把不可能性排除。**

---

## 04｜AI 写的代码：哪些能用，哪些不能

用 AI 写了大半年代码，我总结出一份很朴素的分类。

**可以直接用的：**

- 工具类、转换类、模板代码
- 单元测试，尤其是边界用例——它比人想得全
- 正则表达式（这个是真的强）
- 文档、注释、示例代码
- 重构建议，它经常能指出我们已经习以为常的坏味道

**必须自己过一遍的：**

- 核心业务链路：资金、账务、风控，每一行都要自己看
- 并发与锁的边界
- 事务边界
- 第三方 API 调用——它很擅长编造不存在的参数
- 任何"看起来能跑，但我说不清楚为什么能跑"的代码

**只有一条原则：能生成代码，不等于能生成一个稳定的系统。**

代码能跑只是及格线，异常场景下的行为才是生产环境真正的考卷。

还有一条是我最近才想明白的：

**AI 时代，代码的"作者"变得不那么重要了，"验证者"变得前所未有地重要。**

以前 code review 主要看"这段代码写得对不对"。现在 review 的价值在往上游走：需求拆得对不对？边界想清楚了吗？测试覆盖到资金安全的场景了吗？

这些问题 AI 给不了答案。它们依赖的是 16 年攒下来的那些深夜、故障复盘和线上事故。

## 05｜比"我会用 AI"更重要的，是团队怎么用

个人拥抱 AI 是容易的。难的是让一个团队用好 AI。

我现在带的团队有 40 人左右，横跨前端、后端、测试、数据四个方向。这一年踩过的坑，比读过的文章还多。

**坑一：AI 成了万能背锅侠。**

"这代码是 AI 写的"变成了新的万能借口。但 AI 写的，也是你提交的。**责任永远在人身上，不在模型上。** 这一条必须写进团队规范。

**坑二：大家偷偷用，规则却不存在。**

禁是禁不住的。真实情况是：你还在会议室讨论"要不要规范 AI 用法"，你的工程师已经用它写完三个需求了。

正确姿势不是禁，而是把边界写下来：什么可以贴给 AI，什么绝对不行（生产数据、密钥、内部核心代码），什么必须人工 review。

**坑三：把 AI 当搜索引擎用。**

很多人只让 AI 补代码，不让它进方案讨论。这是最大的浪费。AI 最大的价值不是"替你写"，而是"陪你推演"。

**坑四：工具试点没有 kill date。**

试点必须有时限。两周出数据，有效就留下，无效就砍掉。没有截止日期的试点，最后都会变成沉默的技术债。

我们团队现在的四条做法：

1. **规范先行，迭代演进。** 先把红线画清楚（哪些数据不能出域、AI 生成代码必须 review），细则在实践中慢慢补，不追求一次性写出大而全的政策。
2. **验证左移。** 既然 AI 能大量生成代码，review 的重心就要从"逐行读代码"上移到"设计评审 + 测试策略 + 边界确认"。这件事让我们团队的 QA 角色反而更值钱了——单测和自动化的覆盖要求，比以前更高。
3. **把老手的经验变成团队杠杆。** 资深工程师的价值不只是自己写得好，而是知道 AI 会在哪里出错。我们把"AI 常见错误清单"沉淀成文档，新人踩坑的成本会指数级下降。
4. **小步试点，快速复盘。** 一个项目先跑，一个月后复盘，好就推开，不好就停。

一句话总结：

**AI 时代资深工程师的价值，已经不是"我什么都记得"，而是"我知道什么该信、什么该问、什么必须亲自验证"。**

## 06｜AI 让我想起了当年研究微服务到凌晨的自己

最让我意外的是：AI 没有让我对技术失去兴趣，反而让我想起刚接触 Tomcat、Spring Cloud、微服务时的自己。

那时候没有现成答案。为了搞懂一个服务注册问题，我可以翻很久文档；为了定位一次调用异常，可以看一晚上日志；一个服务终于跑通，能开心很久。

现在学 AI 也一样：

- 怎么让 AI 真正理解我们的项目？
- 怎么让它参与方案设计，而不只是补代码？
- 怎么把它接进编码、测试、排障的完整流程？
- 怎么避免它一本正经地胡说八道？

这些问题同样没有标准答案。

而这恰恰是技术最有意思的地方。

---

## 最后

从 SSH 到前后端分离，从 Spring Boot 到微服务，从云原生到今天的 AI。

我们不是第一次站在技术变化的路口。

AI 会淘汰一部分重复的、标准化的、低价值的工作。但它同样会放大那些愿意学习、理解业务、能做技术判断、愿意对结果负责的人。

所以对做了 16 年 Java 的我来说：

> **AI 不是来替代我的。它是让我从重复劳动里抽身，把精力重新放回"解决问题"这件事上。**

而我也终于找回了那个，会为了一个新技术研究到深夜的自己。
